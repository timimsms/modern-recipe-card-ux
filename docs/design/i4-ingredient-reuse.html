Finding I4 · layout engine · phase 02 · phase 07

Real recipes are not trees. The grid assumes they are.

The convergence grid rests on one load-bearing assumption: a step's inputs occupy contiguous rows. That holds only while every result feeds exactly one consumer. Write "reserve half for later" and the recipe becomes a DAG, no row order makes both consumers adjacent, and the format has no answer. Five answers are rendered below, against the two shapes the problem takes.

Hover a reference chip to light up the row it points at.

The matrix

Left column: node reuse — one step's output feeds two branches that re-converge. Right column: leaf reuse — one ingredient is consumed by two steps at different depths. Verdict

Default to the reference chip. It is the only one that is safe, compact, and renderable everywhere.

It keeps one row for one quantity, which is the property that matters: a cook cannot misread it as needing twice the ingredient, because the ingredient appears once and states its own division. It is the smallest chart of the five on both cases, it needs no SVG, and it degrades to plain text on a phone without losing the dependency.

Its real cost is honest and worth stating: the dependency becomes textual rather than spatial, and the whole argument for this format is that structure is spatial. A chip is a footnote where the grid usually draws a line.

Yes — the two cases want different answers, and the discriminator is not the graph.

This was the useful surprise. Both cases are the same shape to a graph algorithm: one node, two consumers. But the right answer is decided by what the shared thing is, not by the shape of the sharing.

In node reuse the shared thing is a preparation with its own recipe — the vinaigrette has five ingredients and a method. That is not a reuse problem at all; it is a component, and the model already has the mechanism (ComponentRefLeaf, built for I5). Promote it, reference it twice, and the DAG disappears — every table is a tree again.

In leaf reuse the shared thing is one ingredient portioned two ways. Promoting butter to a component with its own table would be absurd. That case wants the chip.

Duplicate-leaf is dangerous. Never make it the default.

Two rows that both read "4 oz (115 g) butter" is a shopping-list error waiting to happen, and the failure mode is silent — you notice at the point where the batter is wrong. Every mitigation available (a bracket, a shared "divided" label, half-disc glyphs, per-row portions) was applied in the rendering above and it is still the strategy most likely to be misread, because the mitigations are all secondary marks on a primary signal that says "two rows, two quantities."

Keep it implemented — some renderers may have no better option — but it should require an explicit opt-in, and the engine should never select it on its own.

The connector does not justify the SVG track on its own.

This was the question the SVG experiment was largely built to answer, so the answer matters. Rendered, the connector is the most truthful strategy — one row, one quantity, and the second dependency drawn as a real edge rather than described. Turn connectors off above and you can see how much information the line is carrying.

But it crosses other cells to get where it is going, and the crossing gets worse exactly as recipes get more complex — the situation where you most need it. At 390px it is unusable in a way the others are merely cramped. And a chart with three or four reuse edges becomes a wiring diagram.

Recommendation: keep connector as an option that only the SVG track implements, but find the SVG track a better reason to exist before Phase 07 — arbitrary-scale print output and a true dendrogram view are both stronger candidates than this. If connectors are its only differentiator, the track is not earning its place in the bake-off.

Split-node has a hidden cost that only appeared when it was drawn.

Modelling the division as an explicit step looks like the principled answer — it keeps the tree honest and adds one cell. What the rendering shows is that the two output lanes must then satisfy contiguity themselves, and that forces their order. In the cornbread the skillet-greasing lane has to be listed first, above the batter lane, even though greasing happens last, because any other order splits the batter's rows in two.

So split-node buys tree-purity by letting the layout dictate the reading order of the ingredient column. That is the same class of mistake as the original format's — geometry driving meaning instead of the other way round.

Subtree duplication is the honest baseline, and it is worth keeping as a measurement.

"Just keep it a tree" costs 13 rows instead of 8 on the vinaigrette — a 63% taller chart — and prints the five vinaigrette ingredients twice, which is the duplicate-leaf safety problem multiplied by five. On leaf reuse it collapses into duplicate-leaf exactly, because a leaf's subtree is one row.

Nobody should ship it. It belongs in the harness as the number the other four are measured against.
